# Gigglegram Code Style & Architecture Guidelines

This file serves as the permanent set of rules resulting from codebase analysis of the Gigglegram project, ensuring consistent style, pattern usage, and architectural alignment.

## 1. NestJS Back-End Architecture

- **Module Structure**: Keep apps modularized. Encapsulate business logic securely into grouped folders inside `src/`. Export shared logic (like types, permissions, common interceptors) via internal monorepo packages (`@repo/common`, `@repo/types`, `@repo/database`).
- **Microservices Communication**:
  - Register clients heavily using `ClientsModule.registerAsync` alongside `ConfigService` reading direct configurations like URLs and listener ports.
  - **Kafka (`Transport.KAFKA`)**: Used for decoupled, event-driven async messaging.
  - **gRPC (`Transport.GRPC`)**: Used for strict, synchronous inter-service communication (e.g. `AUTH_SERVICE_NAME` or `SYSTEM_SETTINGS_SERVICE_NAME`). Always maintain Protobuf (`.proto`) files centralized under `@repo/types/src/proto`.
- **Validation & Guards**: Route access is typically restricted via generic permission guards `PermGuard` paired with the `@Perms()` decorator handling specific resource-level access. Always use `@CurrentUser()` to intercept user context securely.

## 2. Database & Drizzle ORM

- **Schema Definitions**: Define schemas using `drizzle-orm/pg-core` inside `packages/database/src/drizzle/schemas/`. Explicitly declare table fields, indices/composites, and explicitly map cross-table links via the `relations()` function. Categorize domains safely into distinct schema files (e.g., `post-schemas.ts`, `auth-schemas.ts`).
- **Repository Pattern**: Never query the db directly from Nest JS Services. Always query via repositories extending `AbstractRepository`. `AbstractRepository` provides common implementations for `findMany` (including pagination, basic sorting configurations, and calculating `_totalCount`), `findFirst`, `create`, `update`, and `delete`. Create distinct repository classes extending this base per entity.

## 3. Next.js Frontend Framework

- **Structure**: Next.js App Router paradigm. Store domain pages under `/app/`, components mapped to structured buckets: `/components/ui/` (shadcn primitive components), `/components/pages/` (page-specific layout units), and `/components/reui/`.
- **Styling**: Exclusively use **Tailwind CSS**. Leverage **shadcn/ui** for complex interactive and atomic UI components. **Always check for and use existing shadcn built-in components whenever possible** instead of creating custom implementations to avoid reinventing the wheel. Always use semantic brand styles configured via CSS variables in `globals.css` (e.g., use `text-foreground` instead of `text-white`, `bg-background` instead of `bg-white`). Avoid hardcoded color utilities. Always style custom components as explicitly close to the `shadcn/ui` aesthetic as possible.
- **State Management & Data Fetching**: Avoid using `useEffect` for data fetching or complex state synchronization. Since this is Next.js 16.1, prioritize fetching data directly within Server Components and passing the resolved data down to Client Components whenever sufficient. When client-side fetching and caching are necessary, use modern specialized abstractions like **TanStack Query** for server-state caching and fetching loops. When prefetching data on the server with TanStack Query, implement the **HydrationBoundary** pattern to pass the dehydrated state to Client Components.
- **Middleware**: Guard private routing globally using configurations via a `proxy.ts` middleware checking auth sessions securely.
- **Error Propagation**: Always propagate errors to the Next.js built-in `error.js` mechanism. Avoid local error state handling (e.g., checking `if (error)` and returning a custom error UI) within page components or layouts. If data is missing (e.g., `!user`), use the `notFound()` function from `next/navigation` to trigger the `not-found.js` boundary. This ensures a unified and consistent error UX across the application.

## 4. Frontend Data Fetching (Axios)

- Use configured API gateway patterns (`axiosGateway` from `@/lib/axios-config.ts`), avoiding direct `fetch` calls.
- Encapsulate server responses accurately into generic wrapper interfaces such as `OkResponse<T>` and `FindManyResponse<T>` (for pagination).
- **Error Handling**: Use the preconfigured axios interceptor that automatically reads generic response `code` fields, translates them locally using `next-intl`, and displays user-friendly warnings using `sonner` (`toast.error()`).

## 5. CI/CD & GitHub Actions

- Keep continuous delivery pipelines in `.github/workflows/`.
- Pipeline primarily executes authentication on Google Cloud using Workload Identity Federation.
- Uses a matrix-style or sequential build execution via `docker/build-push-action@v6` taking respective `./apps/<appName>/Dockerfile.prod` contexts and pushing built images to Google Artifact Registry (GAR) tagged securely using `github.sha`.

## 6. Docker & Kubernetes Deployments

- **Docker**: Maintain optimized `.prod` and `.dev` dockerfiles under each specific application root (`./apps/*/Dockerfile.prod`).
- **Kubernetes / Helm**: Configuration runs under `k8s/gigglegram/`. Avoid massive raw `.yaml` templates. Wrap all deployments efficiently using Helm `Chart.yaml` and parameterise application environment values via `values.yaml` and `values-dev.yaml`. The deployment pipeline utilizes `helm upgrade --install` with `--set apps.<app-name>.image.tag=${{ github.sha }}` targeting the single uniform Helm chart structure.

## 7. API & Network Routing Guidelines

- **Frontend Axios Calls**: The Next.js frontend uses a powerful `rewrites` layer in `next.config.js`. Do not hardcode external API router URLs in Axios. Always use relative paths starting with `/api` (e.g., `axiosGateway.get('/api/posts/feed')`). Next.js naturally intercepts `/api/*` and forwards it securely to the `API_GATEWAY_URL`.
- **Static Media Delivery**: Avoid compiling full Google Cloud Storage URLs in components manually. Use the local path structures `/video/*` and `/images/*`. Next.js handles `.m3u8`, `.mp4`, and image delivery by rewriting those to `STATIC_VIDEO_ASSETS_URL` and `STATIC_IMAGE_ASSETS_URL` respectively, solving CORS barriers efficiently.
- **Gateway Proxy Mapping**: The backend API Gateway (`apps/api-gateway`) relies on NestJS `MiddlewareConsumer` mappings to proxy inbound HTTP traffic directly to decouple microservices. Standard endpoints currently intercepted include `/auth`, `/posts`, `/feed`, `/users`, `/settings`, and `/real-time`. When drafting new services, assure they are correctly injected into the gateway with `AuthProtectMiddleware` to enforce security.

## 8. Internationalization (i18n) & Localization

- **Translation Storage**: All static text, labels, placeholders, and error messages must be externalized into JSON files located in apps/web/messages/.

- **Dual-Locale Requirement**: For every new feature or UI adjustment, corresponding keys must be created or updated in both en.json (English) and vi.json (Vietnamese).

- **Consistency & Parity**:

Never add a key to one language file without adding the identical key to the other.

Ensure the JSON structure (nesting/namespaces) remains perfectly synchronized between both files to prevent hydration errors or missing translation warnings in the Next.js frontend.

- **Library Usage**: Use next-intl hooks (e.g., useTranslations) in the frontend to consume these keys. Avoid hardcoding strings in TSX/JSX components.

- **Automated/Agent Tasks**: When using antigravity or other AI tools to generate code or UI, the tool must automatically identify new static strings and append the appropriate translations to both apps/web/messages/en.json and apps/web/messages/vi.json.

## 9. Date Handling

- **Library Usage**: Always use the `date-fns` library for any date manipulation, formatting, and arithmetic operations (especially for calculating differences, adding time, etc.). Avoid building custom logic using the native `Date` functionality directly for complex calculations.

## 10. Media Display Standards

- **Aspect Ratio**: To maintain a consistent Instagram-like aesthetic, all images and videos on the frontend must always be displayed in a **3:4 aspect ratio**. Utilize Tailwind CSS utilities like `aspect-[3/4]` and `object-cover` to ensure media fills the container correctly without distortion.
- **Image Rendering**: Always use the **Next.js built-in `Image` component** for all image assets. This ensures optimal image optimization, avoids layout shifts via required width/height or `fill` props, and leverages lazy loading by default. Avoid using the standard `<img>` tag unless there is a specific, documented technical reason to do so.

## 11. Design System Adherence

- **Style Tokens**: All UI components must strictly adhere to the styling tokens and utilities defined in `apps/web/app/globals.css`.
- **Colors**: Use OKLCH color variables (e.g., `text-primary`, `bg-background`, `border-border`) instead of hardcoded hex or Tailwind default colors.
- **Typography & Layout**: Utilize font family variables (e.g., `--font-sans` for Roboto) and shadow/radius tokens (e.g., `--radius`, `--shadow-md`) to ensure visual consistency.
- **Custom Utilities**: Leverage project-specific utilities such as `bg-grid-fade` or `bg-grid-dark` for consistent background patterns across the application.

## 12. Type Safety & TypeScript

- **No `any`**: Never use the `any` type. It defeats the purpose of TypeScript and introduces potential runtime errors.
- **Explicit Annotations**: Provide explicit type annotations for component props, function parameters, and return types.
- **Drizzle Inference**: Leverage `typeof table.$inferSelect` and `typeof table.$inferInsert` from Drizzle for database-related types.
- **Type Utilities**: Use TypeScript's built-in type utilities (e.g., `Partial`, `Pick`, `Omit`, `Record`) to derive types instead of rewriting them.
- **Discriminated Unions**: For states or complex objects, use discriminated unions to handle different logic branches safely.

## 13. Import Standards

- **Path Aliases**: Always use the `@` alias for all internal imports within the `apps/web` directory (e.g., use `@/components/...` instead of `../../components/...` or `./`). This ensures consistency, improves readability, and makes refactoring easier across the codebase.
